# Як зробити нову справу

Справа — це **тека з контентом** плюс, за потреби, нові можливості рушія. Рушій, екрани й список у лобі спільні.
Цей документ — технічні правила й найкращі практики. Він не описує, *якою* має бути справа: сюжет, жанр, структуру й
формати вигадуйте щоразу заново (розділ 1).

## 1. Задум і стиль

Як придумувати справу (без шаблону, з новими форматами), порядок роботи, як говорять персонажі, і як делегувати медіа —
у скілі Claude Code `.claude/skills/new-case/SKILL.md` (виклик `/new-case`). Генерацію фото й аудіо робить агент
`.claude/agents/case-media.md`. Тут — лише технічна частина.

## 2. Структура теки

```
cases/<id>/                 id — латиниця/цифри/дефіс, напр. "lake-house"
  case.json                 документи, правила запитів, питання, бали  (читає рушій)
  documents/                HTML-документи справи: <ID>.html … і _base.css
  photos/                   фото для документів: <ID>.jpg (потрапляють у застосунок); <ID>.png — оригінали (не комітяться)
  avatars/                  картинки персонажів, що «говорять» у відповідях (jpg, ~256 px)
  rules.html                правила для кнопки «i» (фрагмент HTML: <h3>, <p>, <ol>)
  photo_jobs.json           промпти для генерації фото (розділ 5)
  map_jobs.json, maps/      завдання й оверлеї карт — агент `case-map`, довідник `docs/MAPS.md`
  story/                    біблія справи — лише для автора, у застосунок НЕ потрапляє
  semantic_cases.json       (необов'язково) приклади фраз для підбору порогів моделі
```

Нові формати можуть додавати свої теки (напр. `audio/`) — див. розділ 6.

Збірка сама знаходить кожну `cases/*/case.json`: копіює документи/фото, створює тему й картку в лобі.
Картку описує блок `meta` у `case.json`:

```json
"meta": { "card": "Місце, час, зав'язка без спойлерів. Близько 2 годин.", "accent": "#8a2c22", "on_accent": "#f6f1e3" }
```

`card` — короткий опис справи для картки в лобі (без розв'язки). `accent` — головний колір справи (кнопки, виділення), `on_accent` — колір тексту на ньому.

## 3. Порядок роботи

1. **Придумайте справу** в `story/`, у вільній формі. Обов'язково мати для себе: правдиву хронологію (що сталося
   насправді, з точним часом), персонажів із їхніми мотивами й брехнею, каталог доказів (який документ що доводить і
   звідки гравець дізнається ключ, щоб його запросити), етапи й питання, пастки та їх спростування.
   Це найважливіше — гра чесна, лише якщо відповіді на питання справді виводяться з документів.
2. **Документи** (`documents/*.html`) — по одному HTML на документ, спільний стиль `_base.css` (аркуш А4, бланки,
   печатки); для незвичних форматів пишіть власні стилі в самому документі.
   Тексти можна писати в Markdown і конвертувати: `python tools/md2doc.py cases/<id>` (див. шапку скрипта).
   Посилання на фото — `<img src="../photos/S01.jpg">`.
   Як писати тексти (мова персонажів, точність часу й цифр) — у скілі `new-case`.
3. **`case.json`** — зв'яжіть документи, запити й питання (розділ 4).
4. **Фото, аватари, аудіо** — розділ 5.
5. **Перевірка**: напишіть тест повного проходження у `dev/src/test/kotlin/` — `CaseEngine(JSONObject(case.json))`,
   далі `request(...)` (кожен «ключ» має знаходитися гравцем у документах, що відкриті раніше!), `answer(...)`,
   `score()`, `rank()`. Перевірте й хибні шляхи: неправильні відповіді, вгадування без доказів, запити до етапу.
   Запуск: `./gradlew :dev:test`. Потім `./gradlew :dev:run` — пограйте у браузері.
6. `git push` у `main` — CI збере APK і опублікує реліз; застосунок на телефоні запропонує оновитися.

## 4. Формат `case.json`

Верхній рівень:

| Ключ | Що |
|---|---|
| `meta` | картка в лобі (див. вище) |
| `title`, `subtitle` | назва й підзаголовок |
| `categories` | `{ "report": "Рапорти й листи", … }` — групи документів у списку |
| `documents` | `[{ "id": "A01", "title": "…", "cat": "report" }]`; файл `documents/A01.html` |
| `start_documents` | id документів, відкритих на старті |
| `final_documents` | id, що відкриваються після останнього питання |
| `stage_names` | `{ "1": "Етап 1. …", … }` і ще одна назва для фіналу (`кількість питань + 1`) |
| `request_types` | типи запитів: `{ "INT": { "label", "target", "details" } }` — підписи полів форми; набір типів вигадуйте під справу |
| `messages` | стандартні відповіді: `stage_locked`, `already`, `repeat`, `unknown_person` і по одній на кожен тип запиту (відповідь «нічого не знайдено») |
| `persons` | `[{ "id": "anna", "aliases": ["анн", "коваленк"] }]` — як гравці називають людей |
| `person_refusals` | що відповідає людина на допит, якщо нічого нового не пред'явили |
| `suspects` | id людей, яких можна обрати відповіддю «хто вбивця» (відповідь не має називати двох) |
| `semantic_counter`, `semantic_counter_generic` | «нейтральні» фрази для моделі розуміння (необов'язково) |
| `speakers`, `default_speaker`, `speaker_by_type` | хто «говорить» у відповідях: ім'я, `img` з `avatars/`; `speaker_by_type`: `{ "EXP": "expert" }` |
| `rules`, `questions` | далі |

### Правила запитів (`rules`)

Запит гравця — це тип + «кого/що» + деталі. Правило спрацьовує, коли збігаються **всі групи ключів**
(у групі достатньо одного слова):

```json
{ "type": "INT", "match": [["коваленк", "анн"], ["квитанц", "ломбард", "#4471"]],
  "unlock": ["B07"], "stage": 2,
  "requires_any": ["B03"], "blocked": "Анна мовчить. Без документів вона нічого не скаже." }
```

- `type` — ключ із `request_types`; `unlock` — документи, які відкриваються; `stage` — з якого етапу доступно.
- Ключі пишуться як **основа слова** без закінчення (`"коваленк"`): рушій терпить відмінки, одну-дві помилки, латиницю замість кирилиці.
  Короткі ключі (до 4 літер) шукаються лише на початку слова, довші — і всередині. Номери й фрази з пробілом — лише точний збіг;
  `"#4471"` — номер за цифрами, байдуже як записаний.
- `requires_all` / `requires_any` — потрібні документи; поки їх немає, гравець бачить `blocked`.
- `response` замість `unlock` — просто текстова відповідь без нового документа.
- `examples` (+ `person`) — приклади формулювань для моделі розуміння, якщо гравець перефразує (працює, коли в застосунку є модель; без неї вирішують лише ключові слова, тому **ключів має вистачати**).
- `aliases` людей: додавайте зменшувальні й розмовні форми імені («Олександра» → «саш», «сашк»), але перевіряйте, що
  короткий ключ не збігається з поширеними словами.

> Золоте правило: кожен ключ (прізвище, номер, назва організації) має бути **видимий у вже відкритому документі**.

### Питання етапів (`questions`)

Питання іде за порядком; відповідь на кожне відкриває наступний етап. Останнє питання закриває справу
(відкриваються `final_documents`, показується ранг з `ranks`).

```json
{ "id": "Q1", "stage": 1, "title": "…", "intro": "Слідчий: «…»",
  "fields": [ … ], "success": "…", "fail": "…", "fail_penalty": 2,
  "hints": ["підказка 1", "підказка 2"],
  "ranks": [ { "min": 9, "title": "…" }, { "min": -99, "title": "…" } ] }
```

`ranks` — лише в останнього питання, від найвищого `min` до найнижчого. Кожна помилка знімає бали (`fail_penalty`, за замовчуванням 0.5), кожна підказка — 0.5.

`requires_any: ["C01", "C02"]` + `requires_text: "…"` — захист від вгадування: поки не відкрито жодного з цих документів, відповідь
не перевіряється, гравці бачать `requires_text`, бали не знімаються. Варто ставити у фінал — документи етапу, які прямо
вказують на винного (кілька, бо дійти можна різними шляхами).

Поля (`fields[]`), `required: true` — без цього поля відповідь не зараховується:

| `kind` | Перевіряє | Параметри |
|---|---|---|
| `person` | названо саме цю людину й жодного іншого підозрюваного | `person` (id) |
| `time` | усі названі моменти в межах вікна («19:15», «пів на восьму», «між 19 і 21») | `window: ["19:00","20:00"]` (може переходити через північ: `["23:20","00:05"]`); `not_times: ["15.10"]` — дати справи, які інакше сприймуться як час 15:10 |
| `text` | відповідь складається з аргументів-`parts`; частина зараховується за ключами `kw`, за `kw_all` (кілька груп ключів, з кожної має бути хоч один: `[["ключ"], ["зник", "нема"]]`) або `examples` для моделі | `parts`, `min_parts` (скільки частин потрібно), `wrong` (хибні відповіді), `points` або `points_per_part`+`max_points`, `only_person` |

Кожне поле має `id`, `label`, `placeholder`, за потреби `multiline: true`. Потрібен інший вид перевірки (число, місце на
мапі, вибір із фото, розшифроване слово) — додайте новий `kind` в `casekit/.../AnswerJudge.kt` (розділ 6).

Для полів `text` думайте, як відповідатимуть гравці: коротко, своїми словами, називаючи факт, а не документ.
Тестуйте кожне поле кількома реалістичними формулюваннями — правильними й хибними.

## 5. Медіа

### Що потрібно

- **Фото для документів** — портрети, місце події, речові докази. Кадри перелічіть у `story/`.
- **Аватари** персонажів, що «говорять» у відповідях — квадратні, ~256×256, `avatars/<name>.jpg`.
- **Аудіо й інші формати** — за задумом справи (розділ 6 — як їх підключити).

### Обмеження розміру

У збірці з CI медіа документів вантажаться на телефони гравців напряму з репозиторію через **jsDelivr**
(`https://cdn.jsdelivr.net/gh/<repo>@<коміт>/cases/<id>/photos/…`), а не через relay чи телефон хоста. jsDelivr віддає
файли до **20 МБ**; розумні розміри для мобільного інтернету — фото до ~300 КБ, аудіо — кілька МБ (Opus/MP3, моно).
Тому медіа мають бути **закомічені й запушені** — збірка посилається на свій коміт.

Без CDN (локальна збірка, `dev:run`, або гравець без інтернету в режимі Wi-Fi) файли віддає телефон: у Wi-Fi ліміту
немає, а через relay проходять лише файли до **180 КБ** (`RelayClient.MAX_ASSET`). Тож для тестів через relay з
локальної збірки великі файли не покажуться — це нормально.

### Генерація через ComfyUI

Скрипт `tools/comfy_gen.py` ганяє завдання з `photo_jobs.json` через **локальний ComfyUI** (`http://127.0.0.1:8188`)
з моделями Qwen-Image 2.1 (опційно апскейл SeedVR2).

1. Встановіть залежності: `pip install -r tools/requirements.txt`. Запустіть ComfyUI з потрібними моделями.
2. Опишіть кадри в `cases/<id>/photo_jobs.json`:

   ```json
   [
     { "id": "P01", "aspect": "3:4 (Portrait Standard)", "seed": 1101,
       "prompt": "Candid documentary portrait photograph of a 44-year-old … natural light, film grain" },
     { "id": "P02", "aspect": "3:4 (Portrait Standard)", "seed": 1201, "ref": "P01",
       "prompt": "Same woman as in <image1> … " }
   ]
   ```

   - `id` — ім'я файлу (`P01` → `photos/P01.jpg`); `aspect` — пропорції ("3:2 (Photo)", "3:4 (Portrait Standard)", "16:9" через `canvas`);
   - `seed` — щоб кадр можна було відтворити; `ref` — id вже готового фото як **референс обличчя**, щоб людина на різних кадрах була тією самою;
   - промпт пишіть англійською, у стилі «документальне фото»: вік, зовнішність, одяг, світло, об'єктив, зерно. Жорстокість — без натуралізму (ракурс, розмиття, масштабна лінійка).
3. Запуск:

   ```
   python tools/comfy_gen.py cases/<id>            # усе, чого ще немає
   python tools/comfy_gen.py cases/<id> P01 S04    # лише ці
   python tools/comfy_gen.py cases/<id> --force P02
   ```

4. Результат у `cases/<id>/photos/`: `<ID>.png` (оригінал; в git не потрапляє, але **зберігайте — це референси**) і `<ID>.jpg`.
   Скрипт сам стискає jpg до **170 КБ**. Фото, зроблені іншим способом, покладіть у `photos/` як `.png` і запустіть
   `python tools/shrink_photos.py cases/<id>` (або просто стисніть jpg до 170 КБ вручну).
5. Перегляньте результат, перегенеруйте невдалі з іншим `seed` (`--force`), і лише потім комітьте jpg.

Для аудіо (голоси, шуми, атмосфера) так само використовуйте ComfyUI — з TTS-моделлю, що вміє українську, і моделлю
звуків для фону (дощ, траса, шум кафе, тріск рації). Розширте `comfy_gen.py` або напишіть поруч свій скрипт; оригінали
(wav) не комітьте, лише стиснуті файли. Прослухайте кожен запис: вимову імен, наголоси, чи не звучить голос як диктор.

### Поради

- Спершу згенеруйте **портрети** всіх фігурантів, лише потім кадри з ними (через `ref`).
- Тримайте стиль однаковим: одна фраза про камеру/світло/зерно в кожному промпті.
- Документи посилаються на фото відносним шляхом `../photos/<ID>.jpg`; фото вигідно додавати до документа лише там, де воно працює на розслідування (доказ, а не прикраса).
- Якщо текст на зображенні важливий (вивіска, номер, напис) — не покладайтеся на генератор, накладайте текст у HTML.

## 6. Нові формати й механіки

Додавати нове — нормально й бажано. Де що лежить:

- **Копіювання файлів справи в застосунок** — `hub/build.gradle.kts` (зараз `documents/` → `doc/`, `photos/*.jpg` →
  `photo/`, `avatars/`). Нова тека (напр. `audio/`) — додайте сюди.
- **Роздача файлів і захист від спойлерів** — `casekit/.../CaseModule.kt`, `resource()`: документ віддається, лише
  коли відкритий, фото — коли відкритий документ, що на нього посилається. Нові медіа захищайте так само.
  Тип файлу за розширенням — `LocalServer.mimeOf` у `core`.
- **Посилання на CDN** — `CaseSession.mediaLinks()` там же: `src="../photos/…"` стає адресою jsDelivr із запасним
  `onerror` на телефон; адресу пише збірка в `cdn.txt` (`hub/build.gradle.kts`, з `GITHUB_SHA`). Нову теку медіа
  (напр. `audio/`) додайте і в `mediaLinks`, і в копіювання в `hub/build.gradle.kts`.
- **Документ** — це HTML у WebView: `<audio controls src="../audio/R01.opus">`, власні стилі, SVG, легкий JS.
  Інтерактив (розшифрувати, скласти, повернути) можна робити прямо в документі.
- **Логіка запитів, етапів, балів** — `casekit/.../CaseEngine.kt`; **перевірка відповідей** — `AnswerJudge.kt`;
  **розпізнавання слів** — `Matcher.kt`. Зміни там стосуються всіх справ — запускайте всі тести.
- **Інтерфейс** — `core/src/main/assets/web/`.
- Кожну нову можливість покривайте тестом і описуйте тут, у цьому документі, щоб наступна справа могла нею скористатися.

## 7. Як перевірити, що справа проходиться

- Кожен документ із `documents` має файл `documents/<id>.html`; кожна `unlock` вказує на існуючий документ.
- Пройдіть справу тестом (розділ 3, п. 5): запити → відповіді → ранг.
- У `dev:run` перевірте також дивні, але реальні формулювання гравців: відмінки, помилки, латиницю, зменшувальні імена.
- Спойлери: гравці бачать у застосунку лише відкриті документи; решта файлів недоступна навіть за прямим посиланням.

## 8. Випуск

`git add cases/<id> && git commit && git push` → CI збирає APK → `Releases`. Номер версії — номер запуску CI.

## 9. Модель розуміння перефразувань (необов'язково)

Правила з `examples` спрацьовують на перефразування лише з моделлю (paraphrase-multilingual-mpnet, int8 ONNX, ≈150 МБ).
У застосунку вона завжди увімкнена й без перемикачів: при запуску застосунок сам завантажує (по Wi-Fi) і вмикає її, а невдалу спробу повторює при наступному відкритті справи. Файл `semantic-v1.zip` завантажується з релізу
`semantic-v1` один раз і далі працює на телефоні без інтернету. Без моделі вирішують ключові слова — тому в `match` має бути
достатньо ключів, а `examples` — запас для вільних формулювань.

На ПК модель підхопиться з `dev/models/` (`embed.onnx` + `embed.vocab` з архіву). Підбір порогів на прикладах справи:
`./gradlew :dev:test --tests "*SemanticTuning*" -i` (потрібен `cases/<id>/semantic_cases.json` — по `pos`/`neg` фраз на правило).
