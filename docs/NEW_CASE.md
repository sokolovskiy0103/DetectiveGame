# Як зробити нову справу

Справа — це **тека з контентом** плюс, за потреби, нові можливості рушія. Рушій, екрани й список у лобі спільні.
Цей документ — технічні правила й найкращі практики. Він не описує, *якою* має бути справа: сюжет, жанр, структуру й
формати вигадуйте щоразу заново (розділ 1).

## 1. Задум і стиль

Справу роблять агенти під керуванням скілу `new-case` (`.claude/skills/new-case/SKILL.md`); кожен має свій довідник:
біблія — `.claude/skills/new-case/BIBLE.md`, каталог форматів — `docs/FORMATS.md`, медіа — `docs/MEDIA.md`, карти —
`docs/MAPS.md`. Тут — рушій, `case.json`, збірка й перевірка.

## 2. Структура теки

```
cases/<id>/                 id — латиниця/цифри/дефіс, напр. "lake-house"
  case.json                 документи, правила запитів, питання, бали  (читає рушій)
  documents/                HTML-документи справи: <ID>.html … і _base.css
  photos/                   фото й карти для документів: <ID>.jpg (у застосунок)
  avatars/                  картинки персонажів, що «говорять» у відповідях (`speakers`)
  audio/                    звук для документів (<ID>.opus)
  rules.html                правила для кнопки «i» (фрагмент HTML: <h3>, <p>, <ol>)
  photo_jobs.json, audio_jobs.json, map_jobs.json, maps/   завдання генерації — `docs/MEDIA.md`, `docs/MAPS.md`
  story/                    біблія справи — лише для автора, у застосунок НЕ потрапляє
  semantic_cases.json       (необов'язково) приклади фраз для підбору порогів моделі
```

Нові формати можуть додавати свої теки — див. розділ 6.

Збірка сама знаходить кожну `cases/*/case.json`: копіює документи/фото, створює тему й картку в лобі.
Картку описує блок `meta` у `case.json`:

```json
"meta": { "card": "Місце, час, зав'язка без спойлерів. Близько 2 годин.", "accent": "#8a2c22", "on_accent": "#f6f1e3" }
```

`card` — короткий опис справи для картки в лобі (без розв'язки). `accent` — головний колір справи (кнопки, виділення), `on_accent` — колір тексту на ньому.

## 3. Порядок роботи

Конвеєр агентів — у скілі `new-case`. Технічно справа готова, коли:
1. є біблія в `story/` (правдива хронологія, люди, граф доказів, етапи) — гра чесна, лише якщо відповіді справді
   виводяться з документів;
2. є документи `documents/*.html` і медіа, на які вони посилаються;
3. `case.json` зв'язує документи, запити й питання (розділ 4);
4. тест повного проходження в `dev/src/test/kotlin/` — `CaseEngine(JSONObject(case.json))`, далі `request(...)` (кожен
   «ключ» має знаходитися гравцем у документах, що відкриті раніше!), `answer(...)`, `score()`, `rank()`; плюс хибні
   шляхи: неправильні відповіді, вгадування без доказів, запити до етапу. `./gradlew :dev:test`, потім
   `./gradlew :dev:run` — пограти у браузері;
5. `git push` у `main` — CI збере APK і опублікує реліз; застосунок на телефоні запропонує оновитися.

## 4. Формат `case.json`

Верхній рівень:

| Ключ | Що |
|---|---|
| `meta` | картка в лобі (див. вище) |
| `title`, `subtitle` | назва й підзаголовок |
| `categories` | `{ "report": "Рапорти й листи", … }` — групи документів у списку |
| `documents` | `[{ "id": "A01", "title": "…", "cat": "report" }]`; файл `documents/A01.html` |
| `start_documents` | id документів, відкритих на старті |
| `final_documents` | id, що відкриваються після останнього питання |
| `stage_names` | `{ "1": "Етап 1. …", … }` і ще одна назва для фіналу (`кількість питань + 1`) |
| `request_types` | типи запитів: `{ "INT": { "label", "target", "details" } }` — підписи полів форми; набір типів вигадуйте під справу |
| `messages` | стандартні відповіді: `stage_locked`, `already`, `repeat`, `unknown_person` і по одній на кожен тип запиту (відповідь «нічого не знайдено») |
| `persons` | `[{ "id": "anna", "aliases": ["анн", "коваленк"] }]` — як гравці називають людей |
| `person_refusals` | що відповідає людина на допит, якщо нічого нового не пред'явили |
| `suspects` | id людей, яких можна обрати відповіддю «хто вбивця» (відповідь не має називати двох) |
| `semantic_counter`, `semantic_counter_generic` | «нейтральні» фрази для моделі розуміння (необов'язково) |
| `speakers`, `default_speaker`, `speaker_by_type` | хто «говорить» у відповідях: ім'я, `img` з `avatars/`; `speaker_by_type`: `{ "EXP": "expert" }` |
| `rules`, `questions` | далі |

### Правила запитів (`rules`)

Запит гравця — це тип + «кого/що» + деталі. Правило спрацьовує, коли збігаються **всі групи ключів**
(у групі достатньо одного слова):

```json
{ "type": "INT", "match": [["коваленк", "анн"], ["квитанц", "ломбард", "#4471"]],
  "unlock": ["B07"], "stage": 2,
  "requires_any": ["B03"], "blocked": "Анна мовчить. Без документів вона нічого не скаже." }
```

- `type` — ключ із `request_types`; `unlock` — документи, які відкриваються; `stage` — з якого етапу доступно.
- Ключі пишуться як **основа слова** без закінчення (`"коваленк"`): рушій терпить відмінки, одну-дві помилки, латиницю замість кирилиці.
  Короткі ключі (до 4 літер) шукаються лише на початку слова, довші — і всередині. Номери й фрази з пробілом — лише точний збіг;
  `"#4471"` — номер за цифрами, байдуже як записаний.
- `requires_all` / `requires_any` — потрібні документи; поки їх немає, гравець бачить `blocked`.
- `response` замість `unlock` — просто текстова відповідь без нового документа.
- `before_stage: N` — правило діє лише до етапу N: рання відмова в світі справи («Ліка в Мерефі, телефон вимкнено»), яку з етапу N замінює правило з `unlock` (воно йде в списку вище зі `stage: N`). Так кожен етап може мати свою відмову.
- `speaker` — хто відповідає саме на цей запит (ключ із `speakers`), замість звичного для типу з `speaker_by_type`: напр. стеження після повороту веде інша людина.
- `examples` (+ `person`) — приклади формулювань для моделі розуміння, якщо гравець перефразує (працює, коли в застосунку є модель; без неї вирішують лише ключові слова, тому **ключів має вистачати**).
- `aliases` людей: додавайте зменшувальні й розмовні форми імені («Олександра» → «саш», «сашк»), але перевіряйте, що
  короткий ключ не збігається з поширеними словами.

> Золоте правило: кожен ключ (прізвище, номер, назва організації) має бути **видимий у вже відкритому документі**.

### Питання етапів (`questions`)

Питання іде за порядком; відповідь на кожне відкриває наступний етап. Останнє питання закриває справу
(відкриваються `final_documents`, показується ранг з `ranks`).

```json
{ "id": "Q1", "stage": 1, "title": "…", "intro": "Слідчий: «…»",
  "fields": [ … ], "success": "…", "fail": "…", "fail_penalty": 2,
  "hints": ["підказка 1", "підказка 2"],
  "ranks": [ { "min": 9, "title": "…" }, { "min": -99, "title": "…" } ] }
```

`unlock: ["D01"]` (+ `unlock_by` — підпис «ким відкрито») — документи, що відкриваються разом із `success` після правильної відповіді (поворот сюжету). У `case.json` верхнього рівня `final_by` — підпис для `final_documents` (за замовчуванням «Обшук»).

`ranks` — лише в останнього питання, від найвищого `min` до найнижчого. Кожна помилка знімає бали (`fail_penalty`, за замовчуванням 0.5), кожна підказка — 0.5.

`requires_any: ["C01", "C02"]` + `requires_text: "…"` — захист від вгадування: поки не відкрито жодного з цих документів, відповідь
не перевіряється, гравці бачать `requires_text`, бали не знімаються. Варто ставити у фінал — документи етапу, які прямо
вказують на винного (кілька, бо дійти можна різними шляхами).

Поля (`fields[]`), `required: true` — без цього поля відповідь не зараховується:

| `kind` | Перевіряє | Параметри |
|---|---|---|
| `person` | названо саме цю людину й жодного іншого підозрюваного | `person` (id); `also: ["id"]` — спільники, яких можна назвати поруч («Ірина з Костею») |
| `time` | усі названі моменти в межах вікна («19:15», «пів на восьму», «між 19 і 21») | `window: ["19:00","20:00"]` (може переходити через північ: `["23:20","00:05"]`); `not_times: ["15.10"]` — дати справи, які інакше сприймуться як час 15:10; `any_time: true` — досить одного моменту у вікні (гравці пишуть і час із запису, і перерахований: «на записі 04:14, тобто 03:14»); `hour_offset: 0` — справа вночі («о першій» = 01:00, «пів на другу» = 01:30, «3 години ночі»); за замовчуванням слова-години читаються як вечір (+12) |
| `text` | відповідь складається з аргументів-`parts`; частина зараховується за ключами `kw`, за `kw_all` (кілька груп ключів, з кожної має бути хоч один: `[["ключ"], ["зник", "нема"]]`) або `examples` для моделі | `parts`, `min_parts` (скільки частин потрібно), `wrong` (хибні відповіді), `points` або `points_per_part`+`max_points`, `only_person` |

Кожне поле має `id`, `label`, `placeholder`, за потреби `multiline: true`. Потрібен інший вид перевірки (число, місце на
мапі, вибір із фото, розшифроване слово) — додайте новий `kind` в `casekit/.../AnswerJudge.kt` (розділ 6).

Для полів `text` думайте, як відповідатимуть гравці: коротко, своїми словами, називаючи факт, а не документ.
Тестуйте кожне поле кількома реалістичними формулюваннями — правильними й хибними.

## 5. Медіа

Генерує агент `case-media` (фото, аватари, звук) і `case-map` (карти); довідники — `docs/MEDIA.md`, `docs/MAPS.md`.
Для рушія важливо одне: у збірці з CI медіа документів вантажаться на телефони напряму з репозиторію через
**jsDelivr** (`https://cdn.jsdelivr.net/gh/<repo>@<коміт>/cases/<id>/photos/…`, до 20 МБ на файл), тож вони мають
бути **закомічені й запушені** — збірка посилається на свій коміт. Без CDN (локальна збірка, `dev:run`, гравець без
інтернету в режимі Wi-Fi) файли віддає телефон хоста.

## 6. Нові формати й механіки

Додавати нове — нормально й бажано. Де що лежить:

- **Копіювання файлів справи в застосунок** — `hub/build.gradle.kts` (зараз `documents/` → `doc/`, `photos/*.jpg` →
  `photo/`, `avatars/`, `audio/*.opus|mp3`). Нова тека (напр. `video/`) — додайте сюди.
- **Роздача файлів і захист від спойлерів** — `casekit/.../CaseModule.kt`, `resource()`: документ віддається, лише
  коли відкритий, фото чи запис — коли відкритий документ, що на нього посилається. Нові медіа захищайте так само.
  Тип файлу за розширенням — `LocalServer.mimeOf` у `core`.
- **Посилання на CDN** — `CaseSession.mediaLinks()` там же: `src="../photos/…"` стає адресою jsDelivr із запасним
  `onerror` на телефон; адресу пише збірка в `cdn.txt` (`hub/build.gradle.kts`, з `GITHUB_SHA`). Нову теку медіа
  додайте і в `mediaLinks`, і в копіювання в `hub/build.gradle.kts`.
- **Документ** — HTML у WebView (власні стилі, SVG, легкий JS); що в ньому вже можна — `docs/FORMATS.md`.
- **Логіка запитів, етапів, балів** — `casekit/.../CaseEngine.kt`; **перевірка відповідей** — `AnswerJudge.kt`;
  **розпізнавання слів** — `Matcher.kt`. Зміни там стосуються всіх справ — запускайте всі тести.
- **Інтерфейс** — `core/src/main/assets/web/`.
- Кожну нову можливість покривайте тестом і описуйте тут, у цьому документі, щоб наступна справа могла нею скористатися.

## 7. Як перевірити, що справа проходиться

- Кожен документ із `documents` має файл `documents/<id>.html`; кожна `unlock` вказує на існуючий документ.
- Пройдіть справу тестом (розділ 3, п. 4): запити → відповіді → ранг.
- У `dev:run` перевірте також дивні, але реальні формулювання гравців: відмінки, помилки, латиницю, зменшувальні імена.
- Проходження наосліп у консолі (`./gradlew -q :dev:play`, `dev/.../dev/PlayCli.kt`) — так грає агент `case-playtester`.
- Спойлери: гравці бачать у застосунку лише відкриті документи; решта файлів недоступна навіть за прямим посиланням.

## 8. Випуск

`git add cases/<id> && git commit && git push` → CI збирає APK → `Releases`. Номер версії — номер запуску CI.

## 9. Модель розуміння перефразувань (необов'язково)

Правила з `examples` спрацьовують на перефразування лише з моделлю (paraphrase-multilingual-mpnet, int8 ONNX).
У застосунку вона завжди увімкнена

На ПК модель підхопиться з `dev/models/` (`embed.onnx` + `embed.vocab` з архіву). Підбір порогів на прикладах справи:
`./gradlew :dev:test --tests "*SemanticTuning*" -i` (потрібен `cases/<id>/semantic_cases.json` — по `pos`/`neg` фраз на правило).
