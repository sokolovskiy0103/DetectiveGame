# Як зробити нову справу

Справа — це **тека з контентом**. Рушій, екрани й список у лобі спільні; код чіпати не треба.
Еталон — `cases/stairs/`.

## 1. Структура теки

```
cases/<id>/                 id — латиниця/цифри/дефіс, напр. "lake-house"
  case.json                 документи, правила запитів, питання, бали  (читає рушій)
  documents/                HTML-документи справи: A01.html, B02.html … і _base.css
  photos/                   фото для документів: <ID>.jpg (потрапляють у застосунок); <ID>.png — оригінали (не комітяться)
  avatars/                  картинки персонажів, що «говорять» у відповідях (jpg, ~256 px)
  rules.html                правила для кнопки «i» (фрагмент HTML: <h3>, <p>, <ol>)
  photo_jobs.json           промпти для генерації фото (див. розділ 5)
  story/                    біблія справи — лише для автора, у застосунок НЕ потрапляє
  semantic_cases.json       (необов'язково) приклади фраз для підбору порогів моделі
```

Збірка сама знаходить кожну `cases/*/case.json`: копіює документи/фото, створює тему й картку в лобі.
Картку описує блок `meta` у `case.json`:

```json
"meta": { "card": "Місце, час, зав'язка без спойлерів. Близько 2 годин.", "accent": "#8a2c22", "on_accent": "#f6f1e3" }
```

`card` — короткий опис справи для картки в лобі (без розв'язки). `accent` — головний колір справи (кнопки, виділення), `on_accent` — колір тексту на ньому.

## 2. Порядок роботи

1. **Придумайте справу** в `story/`: синопсис, правдива хронологія, персонажі, каталог доказів, етапи й питання.
   Це найважливіше — гра чесна, лише якщо відповіді на питання справді виводяться з документів.
   Зручно доручити це Claude: «Зроби справу за зразком `cases/stairs/story`», і по черзі файли 00–06.
2. **Документи** (`documents/*.html`) — по одному HTML на документ, стиль `_base.css` (аркуш А4, бланки, печатки).
   Допити можна писати в Markdown і конвертувати: `python tools/md2doc.py cases/<id>` (див. шапку скрипта).
   Посилання на фото — `<img src="../photos/S01.jpg">`.
3. **`case.json`** — зв'яжіть документи, запити й питання (розділ 3).
4. **Фото й аватари** — розділ 5.
5. **Перевірка**: скопіюйте тест `dev/src/test/kotlin/.../WalkthroughTest.kt`, замініть запити на свою справу
   (кожен «ключ» має знаходитися гравцем у документах, що відкриті раніше!) і запустіть `./gradlew :dev:test`.
   Потім `./gradlew :dev:run` — пограйте у браузері.
6. `git push` у `main` — CI збере APK і опублікує реліз; застосунок на телефоні запропонує оновитися.

## 3. Формат `case.json`

Верхній рівень:

| Ключ | Що |
|---|---|
| `meta` | картка в лобі (див. вище) |
| `title`, `subtitle` | назва й підзаголовок |
| `categories` | `{ "report": "Рапорти й листи", … }` — групи документів у списку |
| `documents` | `[{ "id": "A01", "title": "…", "cat": "report" }]`; файл `documents/A01.html` |
| `start_documents` | id документів, відкритих на старті |
| `final_documents` | id, що відкриваються після останнього питання |
| `stage_names` | `{ "1": "Етап 1. …", … }` і ще одна назва для фіналу (`кількість питань + 1`) |
| `request_types` | типи запитів: `{ "INT": { "label", "target", "details" } }` — підписи полів форми |
| `messages` | стандартні відповіді: `stage_locked`, `already`, `repeat`, `unknown_person` і по одній на кожен тип запиту (відповідь «нічого не знайдено») |
| `persons` | `[{ "id": "maksym", "aliases": ["максим", "сенишин"] }]` — як гравці називають людей |
| `person_refusals` | що відповідає людина на допит, якщо нічого нового не пред'явили |
| `suspects` | id людей, яких можна обрати відповіддю «хто вбивця» (відповідь не має називати двох) |
| `semantic_counter`, `semantic_counter_generic` | «нейтральні» фрази для моделі розуміння (необов'язково) |
| `speakers`, `default_speaker`, `speaker_by_type` | хто «говорить» у відповідях: ім'я, `img` з `avatars/`; `speaker_by_type`: `{ "EXP": "kvitka" }` |
| `rules`, `questions` | далі |

### Правила запитів (`rules`)

Запит гравця — це тип + «кого/що» + деталі. Правило спрацьовує, коли збігаються **всі групи ключів**
(у групі достатньо одного слова):

```json
{ "type": "INT", "match": [["дзюба", "соломі"], ["довірен", "бланк", "112487"]],
  "unlock": ["B05b"], "stage": 2,
  "requires_any": ["B07"], "blocked": "Соломія мовчить і плаче. Без документів вона нічого не скаже." }
```

- `type` — ключ із `request_types`; `unlock` — документи, які відкриваються; `stage` — з якого етапу доступно.
- Ключі пишуться як **основа слова** без закінчення (`"кульчицьк"`): рушій терпить відмінки, одну-дві помилки, латиницю замість кирилиці.
  Номери й фрази з пробілом — лише точний збіг; `"#672140851"` — номер за цифрами, байдуже як записаний.
- `requires_all` / `requires_any` — потрібні документи; поки їх немає, гравець бачить `blocked`.
- `response` замість `unlock` — просто текстова відповідь без нового документа.
- `examples` (+ `person`) — приклади формулювань для моделі розуміння, якщо гравець перефразує (працює, коли в застосунку є модель; поки що її немає — вирішують лише ключові слова, тому **ключів має вистачати**).

> Золоте правило: кожен ключ (прізвище, номер, назва організації) має бути **видимий у вже відкритому документі**.

### Питання етапів (`questions`)

Питання іде за порядком; відповідь на кожне відкриває наступний етап. Останнє питання закриває справу
(відкриваються `final_documents`, показується ранг з `ranks`).

```json
{ "id": "Q1", "stage": 1, "title": "…", "intro": "Стасюк: «…»",
  "fields": [ … ], "success": "…", "fail": "…", "fail_penalty": 2,
  "hints": ["підказка 1", "підказка 2"],
  "ranks": [ { "min": 9, "title": "Слідчий року" }, { "min": -99, "title": "Справа стала «глухарем»" } ] }
```

`ranks` — лише в останнього питання, від найвищого `min` до найнижчого. Кожна помилка знімає бали (`fail_penalty`, за замовчуванням 0.5), кожна підказка — 0.5.

Поля (`fields[]`), `required: true` — без цього поля відповідь не зараховується:

| `kind` | Перевіряє | Параметри |
|---|---|---|
| `person` | названо саме цю людину й жодного іншого підозрюваного | `person` (id) |
| `time` | усі названі моменти в межах вікна («19:15», «пів на восьму», «між 19 і 21») | `window: ["19:00","20:00"]` (може переходити через північ: `["23:20","00:05"]`); `not_times: ["15.10"]` — дати справи, які інакше сприймуться як час 15:10 |
| `text` | відповідь складається з аргументів-`parts`; частина зараховується за ключами `kw` (або `examples` для моделі) | `parts`, `min_parts` (скільки частин потрібно), `wrong` (хибні відповіді), `points` або `points_per_part`+`max_points`, `only_person` |

Кожне поле має `id`, `label`, `placeholder`, за потреби `multiline: true`.

## 4. Як перевірити, що справа проходиться

- Кожен документ із `documents` має файл `documents/<id>.html`; кожна `unlock` вказує на існуючий документ.
- Пройдіть справу тестом (розділ 2, п. 5): запити → відповіді → ранг.
- У `dev:run` перевірте також дивні, але реальні формулювання гравців: відмінки, помилки, латиницю.
- Спойлери: гравці бачать у застосунку лише відкриті документи; решта файлів недоступна навіть за прямим посиланням.

## 5. Зображення

### Що потрібно

- **Фото для документів** — портрети, місце події, речові докази. Кадри перелічіть у `story/06_photo_prompts.md`.
- **Аватари** персонажів, що «говорять» (слідчий, експерт) — квадратні, ~256×256, `avatars/<name>.jpg`.

### Генерація через ComfyUI

Скрипт `tools/comfy_gen.py` ганяє завдання з `photo_jobs.json` через **локальний ComfyUI** (`http://127.0.0.1:8188`)
з моделями Qwen-Image 2.1 (опційно апскейл SeedVR2).

1. Встановіть залежності: `pip install -r tools/requirements.txt`. Запустіть ComfyUI з потрібними моделями.
2. Опишіть кадри в `cases/<id>/photo_jobs.json`:

   ```json
   [
     { "id": "P01", "aspect": "3:4 (Portrait Standard)", "seed": 1101,
       "prompt": "Candid documentary portrait photograph of a 44-year-old … natural light, film grain" },
     { "id": "P02", "aspect": "3:4 (Portrait Standard)", "seed": 1201, "ref": "P01",
       "prompt": "Same woman as in <image1> … " }
   ]
   ```

   - `id` — ім'я файлу (`P01` → `photos/P01.jpg`); `aspect` — пропорції ("3:2 (Photo)", "3:4 (Portrait Standard)", "16:9" через `canvas`);
   - `seed` — щоб кадр можна було відтворити; `ref` — id вже готового фото як **референс обличчя**, щоб людина на різних кадрах була тією самою;
   - промпт пишіть англійською, у стилі «документальне фото»: вік, зовнішність, одяг, світло, об'єктив, зерно. Жорстокість — без натуралізму (ракурс, розмиття, масштабна лінійка).
3. Запуск:

   ```
   python tools/comfy_gen.py cases/<id>            # усе, чого ще немає
   python tools/comfy_gen.py cases/<id> P01 S04    # лише ці
   python tools/comfy_gen.py cases/<id> --force P02
   ```

4. Результат у `cases/<id>/photos/`: `<ID>.png` (оригінал; в git не потрапляє, але **зберігайте — це референси**) і `<ID>.jpg`.
   Скрипт сам стискає jpg до **170 КБ**: режим «Інтернет» (relay) не пропускає файли більші за 180 КБ.
   Фото, зроблені іншим способом, покладіть у `photos/` як `.png` і запустіть `python tools/shrink_photos.py cases/<id>`
   (або просто стисніть jpg до 170 КБ вручну).
5. Перегляньте результат, перегенеруйте невдалі з іншим `seed` (`--force`), і лише потім комітьте jpg.

### Поради

- Спершу згенеруйте **портрети** всіх фігурантів, лише потім кадри з ними (через `ref`).
- Тримайте стиль однаковим: одна фраза про камеру/світло/зерно в кожному промпті.
- Документи посилаються на фото відносним шляхом `../photos/<ID>.jpg`; фото вигідно додавати до документа лише там, де воно працює на розслідування (доказ, а не прикраса).

## 6. Випуск

`git add cases/<id> && git commit && git push` → CI збирає APK → `Releases`. Номер версії — номер запуску CI.

## 7. Модель розуміння перефразувань (необов'язково)

Правила з `examples` спрацьовують на перефразування лише з моделлю (paraphrase-multilingual-mpnet, int8 ONNX, ≈150 МБ).
У застосунку вона вмикається сама при першому відкритті справи на Wi-Fi, а хост керує нею кнопкою «🧠 Увімкнути» на вкладці «Запит»: файл `semantic-v1.zip` завантажується з релізу
`semantic-v1` один раз і далі працює на телефоні без інтернету. Без моделі вирішують ключові слова — тому в `match` має бути
достатньо ключів, а `examples` — запас для вільних формулювань.

На ПК модель підхопиться з `dev/models/` (`embed.onnx` + `embed.vocab` з архіву). Підбір порогів на прикладах справи:
`./gradlew :dev:test --tests "*SemanticTuning*" -i` (потрібен `cases/<id>/semantic_cases.json` — по `pos`/`neg` фраз на правило).
Нині на «Сходах»: ключові слова — 19 з 37 перефразувань, з моделлю — 33, хибних спрацювань 0.
